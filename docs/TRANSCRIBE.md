# 問題の書き写し手順(サブエージェント向け)

IPAの応用情報技術者試験 午前(科目A)の問題PDFは、コピー禁止の設定で暗号化されていてテキストを取り出せない。
そこで、ページ画像を読んで問題を書き写し、同時に解説などを書いてJSONにする。

## 入力
- ページ画像: `data-src/pages/{回ID}/pg-NN.png`(150dpi。NN はPDFのページ番号、01始まり)
- 元のPDF: `data-src/pdf/{回ID}_qs.pdf`
  - 文字が読みにくいときは拡大画像を作ってよい:
    `pdftoppm -r 300 -f N -l N -png data-src/pdf/{回ID}_qs.pdf /tmp/zoom`
  - **PDFの保護を解除するコマンド(qpdf --decrypt など)は使わない。**
- 担当する問番号と、その正解(解答PDFから機械的に取ったもの。これを正として解説を書く)

## やること
担当範囲の各問について、下の形式のオブジェクトを作り、配列にして指定のファイルへ書き出す。
書き出したら `node -e "JSON.parse(require('fs').readFileSync('ファイル','utf8'))"` で壊れていないか確かめる。

```json
{
  "no": 3,
  "pdfPage": 5,
  "hasFigure": false,
  "modified": false,
  "stem": "問題文",
  "choices": ["アの文", "イの文", "ウの文", "エの文"],
  "minor": "中分類名",
  "explanation": "正解の理由",
  "whyWrong": ["アの正誤理由", "イの正誤理由", "ウの正誤理由", "エの正誤理由"],
  "analogy": "業務たとえ",
  "terms": [{ "name": "用語", "definition": "1〜2文の定義" }]
}
```

## 書き写しのルール
- **問題文・選択肢は原文どおり。** 句読点(，。)、かっこ、引用符(“ ”)、全角・半角も原文に合わせる。直してよいのは改行位置だけ。
- `stem` には「問3」などの問番号を入れない。選択肢の「ア」「イ」などの記号も `choices` に入れない。
- `pdfPage` は問題文が始まるページの番号。
- 表は次の形式で書く。行頭と行末の `|` を忘れない。前後は空行で区切る。
  ```
  | 列1 | 列2 |
  |---|---|
  | 値 | 値 |
  ```
- 上付き・下付き(2の8乗、log₂ など)は `2^8`、`log_2 n` のように書く。分数は `a/b`。
- 選択肢が表になっている問題(「a と b の組合せ」など)は、各選択肢を `a：〇〇，b：△△` の形で書く。
- 表・数式・選択肢の表記を上のように変えたときは `"modified": true` にする(アプリ上で「表記を一部改変」と表示する)。
- **図(グラフ、回路図、フローチャート、E-R図、ネットワーク構成図など)がないと解けない問題**は `"hasFigure": true` にする。その場合も文章部分は書き写し、図の位置に `（図は原文参照）` と書く。表だけなら図扱いにしない。
- 読み取りに自信がない文字があれば、拡大画像で確認する。それでも不明なら、その問題の報告に書く。

## 解説などのルール
読み手は、ITパスポートと情報セキュリティマネジメントに合格済みの、ベンチャー企業のバックオフィス職(非エンジニア)。
- `minor`: 次の23個のどれか1つを、文字どおりに書く。
  基礎理論 / アルゴリズムとプログラミング / コンピュータ構成要素 / システム構成要素 / ソフトウェア / ハードウェア / ユーザーインタフェース / 情報メディア / データベース / ネットワーク / セキュリティ / システム開発技術 / ソフトウェア開発管理技術 / プロジェクトマネジメント / サービスマネジメント / システム監査 / システム戦略 / システム企画 / 経営戦略マネジメント / 技術戦略マネジメント / ビジネスインダストリ / 企業活動 / 法務
  - 問1〜50はテクノロジ系(上から13個)、問51〜60はマネジメント系(14〜16個目)、問61〜80はストラテジ系(17〜23個目)から選ぶ。
- `explanation`: 3〜5文。ITパスポート程度の前提知識で分かる言葉で。正解がなぜ正しいかを書く。
  - 計算問題は、式を1行ずつ順に書く(改行は `\n`)。
- `whyWrong`: 選択肢ごとに1〜2文。正解の選択肢には「正しい。」で始めて要点を一言。誤りの選択肢は「それは何の説明か」まで書く(別の用語の説明になっていることが多い)。
- `analogy`: 2〜3文。「あなたの仕事で言うと」の欄に出る。ベンチャー企業のバックオフィスの場面にたとえる(PCの貸与・回収、SaaSのアカウント管理、契約書のやり取り、入退社手続き、経費精算、備品の発注など)。
  - 実在の社名・個人名・特定の会社の内情は書かない。
  - 純粋な計算問題などでたとえが苦しいときは、無理にたとえず「解き方のコツ:」で始めて覚え方・解き方を書く。
- `terms`: その問題の鍵になる用語を1〜3個。`definition` は1〜2文。用語名は一般的な表記にする(例: 「ROC曲線」「CRC」)。
- 解説は正確さ最優先。確信が持てない内容は書かない。

## 報告
作業後、次を短く報告する。
- 書き出したファイルと件数
- `hasFigure: true` にした問番号
- 読み取りに不安が残った箇所(なければ「なし」)
